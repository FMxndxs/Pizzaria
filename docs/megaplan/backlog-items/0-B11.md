# 0-B11: Validador de transição de status

## Business Outcome
Uma função testada (`canTransition`) rejeita transições ilegais de status, e `nextStatuses` informa quais transições são permitidas a partir de um estado atual — levando em conta o `fulfillment_type`.

## Scope
- Adiciona ao `src/lib/orders/stateMachine.ts` (criado em 0-B2):
  - `TRANSITIONS`: mapa `{ [from: OrderStatus]: { delivery: OrderStatus[], pickup: OrderStatus[] } }`.
  - `canTransition(from, to, fulfillmentType): boolean`.
  - `nextStatuses(from, fulfillmentType): OrderStatus[]`.
- Tabela de transições (fonte única):
  - `pending` → `confirmed` | `cancelled` (ambos)
  - `confirmed` → `preparing` | `cancelled` (ambos)
  - `preparing` → `ready` | `cancelled` (ambos)
  - `ready` (delivery) → `out_for_delivery` | `cancelled`
  - `ready` (pickup) → `delivered` | `cancelled`
  - `out_for_delivery` → `delivered` | `cancelled`
  - `delivered` → [] (terminal)
  - `cancelled` → [] (terminal)
- **Não inclui:** a chamada dessas funções nas Server Actions (→ A-B5); a State Machine como guard do banco.

## Dependencies
- 0-B2 (`stateMachine.ts` com metadata; `OrderStatus` com `ready`)
- 0-B10 (para `FulfillmentType` importado)

## Test Plan
### Unit
- `canTransition('pending', 'confirmed', 'delivery')` → `true`.
- `canTransition('pending', 'delivered', 'delivery')` → `false` (pulo ilegal).
- `canTransition('ready', 'out_for_delivery', 'delivery')` → `true`.
- `canTransition('ready', 'out_for_delivery', 'pickup')` → `false` (pickup não tem esse estado).
- `canTransition('ready', 'delivered', 'pickup')` → `true`.
- `canTransition('delivered', 'cancelled', 'delivery')` → `false` (terminal).
- `nextStatuses('preparing', 'delivery')` → `['ready', 'cancelled']`.
- `nextStatuses('delivered', 'pickup')` → `[]`.

## Acceptance Criteria
- [ ] Todos os casos de teste unitário passam.
- [ ] Nenhuma transição terminal tem `nextStatuses` não-vazio.
- [ ] `pickup` nunca tem `out_for_delivery` em `nextStatuses`.
- [ ] Docs atualizados.

## Implementation Notes
Esta função é a ÚNICA fonte de verdade sobre transições legais. Qualquer servidor (Action, REST), UI (dropdown), e documentação deve derivar de `canTransition`/`nextStatuses` — nunca duplicar a tabela.

A validação de transição acontece no service layer (TS), não via trigger de banco (BEFORE UPDATE plpgsql) — decisão de MVP documentada no plano. O comentário `// TODO: DB-level guard - see ADR-003` pode ser adicionado no service.
