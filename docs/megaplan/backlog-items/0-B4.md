# 0-B4: Trigger de histórico de status

## Business Outcome
Toda mudança de `orders.status` — independente de qual camada a fez — é automaticamente registrada em `order_status_history`, com timestamp e autor.

## Scope
- Cria função `record_order_status_history()` como `SECURITY DEFINER`.
- Cria trigger `AFTER INSERT ON orders` → grava o status inicial `pending`.
- Cria trigger `AFTER UPDATE ON orders WHEN (OLD.status IS DISTINCT FROM NEW.status)` → grava o novo status.
- Ambos capturam `auth.uid()` como `changed_by` (null para contexto anon/system — aceitável no MVP).
- Atualiza `docs/database/migrations/003_order_status_history.sql` e `schema.sql`.
- **Não inclui:** lógica de validação de transição (→ 0-B11).

## Dependencies
- 0-B3 (tabela `order_status_history` existe)

## Test Plan
### Manual
- Inserir um pedido via SQL → `order_status_history` deve ter 1 linha com `status='pending'`.
- Atualizar `orders.status` para `confirmed` → nova linha com `status='confirmed'`.
- Atualizar `orders.status` para `confirmed` novamente (sem mudança) → nenhuma nova linha (cláusula `IS DISTINCT FROM`).

## Acceptance Criteria
- [ ] INSERT em `orders` gera linha em `order_status_history` com `status='pending'`.
- [ ] UPDATE de status gera nova linha.
- [ ] UPDATE sem mudança de status não gera linha.
- [ ] `schema.sql` atualizado.
- [ ] Docs atualizados.

## Implementation Notes
O trigger deve ser `SECURITY DEFINER` para contornar a RLS de INSERT na tabela de histórico (policy regular bloqueia INSERT direto). A função executa com os privilégios do owner do schema, não do caller.

`auth.uid()` retorna NULL quando a sessão não tem JWT (ex.: SQL Editor sem autenticação). Isso é esperado e documentado no ADR-003 como limitação aceitável no MVP.
