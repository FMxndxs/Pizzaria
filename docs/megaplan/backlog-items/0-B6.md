# 0-B6: Backfill + unicidade do número de pedido

## Business Outcome
Pedidos existentes recebem números de pedido retroativos e a coluna torna-se `NOT NULL UNIQUE`, garantindo que nenhum pedido futuro fica sem número.

## Scope
- Backfill: `UPDATE orders SET order_seq = nextval('order_code_seq'), order_code = '#' || gen_order_code(nextval...) WHERE order_code IS NULL ORDER BY created_at`.
- Altera coluna: `ALTER TABLE orders ALTER COLUMN order_code SET NOT NULL`.
- Adiciona: `ALTER TABLE orders ADD CONSTRAINT orders_order_code_key UNIQUE (order_code)`.
- Adiciona índice: `CREATE UNIQUE INDEX IF NOT EXISTS orders_order_code_idx ON orders(order_code)`.
- Atualiza `schema.sql`.
- **Não inclui:** exposição no painel (→ A-B9).

## Dependencies
- 0-B5 (sequence e função `gen_order_code` existem; trigger ativo para novos pedidos)

## Test Plan
### Manual
- Nenhum pedido tem `order_code IS NULL` após o backfill.
- Tentativa de INSERT com `order_code` duplicado retorna erro de unique constraint.
- Tentativa de INSERT sem `order_code` (trigger desabilitado artificialmente) retorna erro NOT NULL.

## Acceptance Criteria
- [ ] `SELECT COUNT(*) FROM orders WHERE order_code IS NULL` retorna 0.
- [ ] Constraint UNIQUE existe em `orders.order_code`.
- [ ] `schema.sql` reflete `NOT NULL UNIQUE` na coluna.
- [ ] Docs atualizados.

## Implementation Notes
O backfill precisa ser feito **antes** de adicionar `NOT NULL`. Ordem na migration: 1) backfill UPDATE, 2) `SET NOT NULL`, 3) `ADD CONSTRAINT UNIQUE`.

Se houver muitos pedidos, o UPDATE pode ser lento — no MVP (poucas linhas) não é problema. Para produção futura, considerar batching.
