# 0-B8: Coluna `profiles.role` + backfill

## Business Outcome
Cada perfil de usuário tem um papel explícito (`owner`, `operator` ou `kitchen`), substituindo o boolean `is_admin` como mecanismo de controle de acesso.

## Scope
- Cria tipo `CREATE TYPE user_role AS ENUM ('owner', 'operator', 'kitchen')` (guard).
- Adiciona coluna `profiles.role user_role NOT NULL DEFAULT 'operator'`.
- Backfill: `UPDATE profiles SET role = 'owner' WHERE is_admin = true`.
- **Mantém** a coluna `is_admin` (drop é migration futura, após o app migrar completamente).
- Atualiza `docs/database/migrations/004_profiles_role.sql` (novo arquivo) e `schema.sql`.
- Atualiza `src/types/index.ts`: adiciona `UserRole = 'owner' | 'operator' | 'kitchen'` e `role` à interface `UserProfile`.
- **Não inclui:** helpers SQL `is_owner`/`is_staff` (→ 0-B9); atualização do middleware (→ durante Cycle B/A).

## Dependencies
- Nenhuma (independente do enum de status).

## Test Plan
### Unit
- `UserProfile` type tem `role: UserRole`.
### Manual
- `SELECT id, is_admin, role FROM profiles` mostra `role='owner'` para quem tem `is_admin=true`, `role='operator'` para os demais.

## Acceptance Criteria
- [ ] Coluna `role` existe em `profiles` com `NOT NULL DEFAULT 'operator'`.
- [ ] Usuários com `is_admin=true` têm `role='owner'` após backfill.
- [ ] `UserRole` e `role` exportados de `src/types/index.ts`.
- [ ] `schema.sql` atualizado.
- [ ] Docs atualizados.

## Implementation Notes
Default `operator` é intencional: não há signup público de staff. Novos usuários provisionados manualmente terão o papel ajustado pelo owner. Ver Glossário → "RBAC / Papel".

A coluna `is_admin` é mantida para que o middleware e layout existentes continuem funcionando sem quebrar enquanto 0-B9 não atualiza os helpers SQL.
